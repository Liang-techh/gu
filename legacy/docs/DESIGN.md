# 青茅山沙盒：规则与扩展约定

## 1. 原文层与改编层分开

原文依据来自用户仓库第一卷已读取的第 5、6、7、8、10、12、14、20、23、39、40 章等相关段落，不以外部百科或模型记忆取代原文。已用人物、地点、蛊名和核心术语在 `content.js` 中附章节。普通界面描述、分支叙述与游戏时间表是原创组合，不声称逐字摘自小说。

原文确认的区别包括：甲乙丙丁资质；空窍与元海；真元作为催动和炼化的资源；初、中、高、巅峰阶段；第一只炼化的本命蛊；未炼成的蛊虫会抵抗；月光蛊吞食月兰花瓣；酒虫饮酒；知心草可辅助节省食料。数值、概率、回合伤害、升级速度及人物态度模型均另标为游戏化规则。

原文没有核对清楚的蛊方、食料和高阶机制，不用听起来相似的自创名称补齐。本版两种蛊确实能玩，不将目录中的所有原著术语误算为已实现蛊虫。

## 2. 状态不是日志

状态包含 `v`、`bag`、`market`、`gu`、`npcs`、`flags`、`queue`、`pending`、`combat`、`rng` 等。长期关系、互斥路线和债务独立保存；截断最近日志不会让系统忘掉它们。

开局展示的 134 个状态字段由 40 个核心变量、7 种背包资源、7 种市场存量、18 个剧情标记、6 个统计字段、7 位人物各 7 个数值以及一只蛊的 7 个数值/标记字段组成。取得酒虫增加 7 个字段。该计数不是独立剧情的数量，也不把日志数组长度算作新变量。

人物拥有信任、畏惧、敌意、人情、资源、实力、修行进度和最近八次交互记忆。当前仅有轻量的每日资源与修行推进，不宣称有完整自主规划、自由对话、全世界模拟或语言模型代理。

## 3. 条件与延迟后果

事件是只读数据：`id/title/text/choices/locations/requires`。条件为 `[路径, 运算符, 值]`，只接受内置比较，不运行 `eval` 或动态脚本。

选项效果支持 `add/items/relation/set/gu/schedule/combat/special`。先验证条件与成本，再在状态副本上执行；失败返回原状态，时间和随机数都不前进。

延迟队列项记录事件 ID、可触发时间和先前选择的文字起因。每次行动结束检查队列：时间到了但地点不符则保留；事件出现后锁住其他行动，必须先选择。事件暂停时世界也暂停，关闭网页不进行离线扣费。

同一个事件在队列中去重，避免连续点击重复生成订单。已兑现事件不得再次直接领取；显式后续事件可在新的债务或纠纷中再次排入。债务清偿会清掉尚未触发的追债事件。

## 4. 核心分支图

```text
同窗
  帮助方正 → 信任 + 人情 → 后来可求援 / 可请作证
  收费     → 元石 + 失去交情 → 对应选项锁定

钱袋
  归还 → 漠北人情 → 可帮助考核
  私吞 → 48 小时后追问
      归还 → 承担信任损失
      否认 → 敌意上升 → 48 小时后归途冲突
      欠账 → 到期 → 还款 / 延期 / 劳作 / 赖账

酒虫
  立即捕捉 → 得蛊，但失去当次领路机会
  跟踪 → 石缝 → 遗藏
      独占 → 得蛊与元石 → 竞争者与家族盘问
      分享 → 方源取酒虫 → 交易与守密承诺
      上交 → 家族接管 → 食料 / 指导 / 元石奖励

商队
  预订 → 已付订金 → 留酒养蛊 / 转卖获利
  接订单 → 预付款 → 交货 / 退款 / 侵吞
      交货 → 信任 + 补货 + 价格变化
      侵吞 → 商队回应 → 赔偿 / 关系关闭
```

这些分支在 `tests/engine.test.cjs` 中直接检查后续选项、资源归属、事件队列与价格差异，不只比较日志文案。

## 5. 时间、经济与战斗

每次合法行动按整小时推进，跨日只结算一次。真元容量随资质、阶段和境界变化；伤势与疲劳降低效率。六转及以后未实现，五转巅峰处明确停止升级，防止数组越界。

蛊虫饥饿以食料间隔推进，自动养蛊会真实扣库存，缺粮损伤生机。本命蛊死亡伤害持有者。背包空了不能继续凭空喂养。酒虫的精炼只在一转生效。

买卖使用统一价格函数，卖价折半；有限存货、到货与违约改变供应。劳作偿债不同时发放现金，借款不因赖账自动消失。突破失败保留部分修为，不静默升到未实现的境界。

战斗有独立状态，阻止旅行、购物等绕过战斗。月刃检验炼化、生机与真元；失败逃跑受到反击；防守不能免费恢复资源。胜负、伤势与食物收获进入同一状态。

## 6. 存档与输入

JSON 存档保存随机状态，不重新掷骰子。导入限制体积、层级、字段类型、资源范围、已知地点、事件、人物及蛊虫；拒绝危险原型键。界面一律转义玩家名字与导入文本。三个手动槽与自动槽分离；检测到另一标签页写入后暂停自动保存，避免互相覆盖。

没有真正的多人防作弊需求，JSON 编辑并非密码学防篡改。结构验证不等于证明每份存档一定由合法行动产生。

## 7. 添加内容的最小步骤

1. 从 `reference/novel` 找到所用专名，加入出处索引；完整仓库运行 `npm run check:canon`。
2. 在变量词典中注明新字段影响哪项真实规则，避免装饰性数字。
3. 给事件设置地点、资源、人物和前置标记条件；明确互斥资源的归属。
4. 给选择添加即时成本、长期标记及延迟事件，并展示限制原因。
5. 加测试：相同种子、相同初始状态，只改变这个选择，证明后续不同。
6. 有新存档字段时更新版本和显式迁移策略，不默默接纳旧结构。

## 8. 本次验证边界

规则：32 项 Node 测试通过，包括十二种种子的长序列模拟。界面：离线 Chromium DOM 检查通过，覆盖开局、炼化、七页签、移动端布局和转义。网页导航被运行环境策略阻止，因此真实 HTTP 导航、实际持久化重启和在线部署未验证；离线 UI 检查使用了显式存储替身。

完整原著目录没有复制进运行容器。术语在仓库读取时核对，另提供只读自动校验脚本供完整检出环境运行，不把脚本“已写好”说成自动校验“已通过”。
