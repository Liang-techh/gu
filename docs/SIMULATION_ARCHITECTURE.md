# 蛊真人 simulation-first RPG 架构

## 核心原则

玩家不是在一棵剧情树上选择下一页，而是在一组持续运行的状态上采取行动。小说原文提供青茅山、开窍大典、方源、方正、学堂、家族和遗藏等内容素材；引擎只提供通用规则，让这些素材在状态变化中重新组合。

```text
输入 / UI / 将来的 AI 意图
          ↓
安全意图解析（只生成 command，不改状态）
          ↓
SimulationKernel.dispatch
          ↓
Action + Event + Component Systems
          ↓
WorldState（时钟、实体、组件、记忆、关系、势力、导演）
          ↓
Projection / UI / 存档 / 日志
```

## 状态模型

`entities[id]` 是统一实体表。玩家和 NPC 都使用相同的组件形状。`src/engine.js` 提供类似 Qud `Parts` 的组件查询、类似 `Events` 的领域事件流，以及可注册的 GoalHandler 和 InteractionHandler；`simulation.js` 只是当前世界规则的一个实现，而不是把扩展点锁死在 UI 或剧情文本里。

组件默认值由 `src/entity.js` 的实体工厂集中创建，区域人口构建器只注入内容种子。这样新增 NPC、敌对生物或未来的非人实体时，可以复用同一身体、需求、记忆和能力组件，而不需要在世界规则里复制一份对象形状。

世界内容位于独立的 `src/content.js` 内容包，并带有 `CONTENT_INDEX` 与版本号。当前内容包已经从青茅山扩展到白骨山、商家城、三叉山、天梯山，以及第三卷北原草原、黑家军营、王庭福地和八十八角真阳楼的首批区域链。地点、人口表、势力、人物、蛊虫和原文来源因此可以逐包替换或增加；存档记录内容包 ID，避免规则版本和世界素材无声漂移。

区域初始化由 `src/zone-builder.js` 负责：地点标签决定基础资源和危险度，人口表决定环境居民，构建器接收随机源和实体工厂而不依赖 UI。以后可以为不同内容包替换区域构建策略，或在存档恢复/新区域生成时重复调用同一规则。

`src/history.js` 单独维护历史账本：重大领域事件进入有限长度的历史序列，跨日时保存势力和区域快照，UI 只读取摘要。这样日志可以滚动、界面可以更换，而世界发生过什么仍然是存档中的一等状态。

## 系统管线

`src/engine.js` 还提供按阶段注册的 system registry。当前每个小时依次运行 `playerNeeds` 和 `npcSimulation`，跨过世界日时运行 `worldDailyTick`，再由导演观察完整的结算结果。系统有明确优先级，因而新增生产、疾病、天气、追捕或区域生态系统时，不必继续把规则塞进单一 `advance()` 分支；同一管线也能被测试、回放和未来的批量世界模拟调用。

动作也通过同一运行时注册。当前委托接受/交付、商家城演武、三王传承闯关、北原巡逻、真阳楼闯层和内容驱动对话已经由 Action Registry 调度；未迁移的基础动作仍走兼容分支。迁移策略是先把有独立资源、事件和失败后果的动作注册化，再逐步消除旧的条件链。

对话定义位于内容包的 `CONVERSATION_DEFS`，由 `src/conversation.js` 根据地点、旗标、时间和关系门槛筛选。选项后果不直接操作 UI，而是通过关系、势力、记忆和 History 账本写入世界状态。

第二卷的演武场和三王传承使用持续系统而不是一次性分支：`arena` 保存比赛、胜负、连胜和声望；`inheritance` 保存尝试次数、轮次、难度、发现和完成状态。每次行动都经过同一个 dispatch、资源、伤势、记忆和历史管线。

玩家和 NPC 都使用相同的组件形状：

- `identity`：名字、角色、标签。
- `position`：地点。
- `needs`：精力、饥饿、安全感。
- `cultivation`：资质、境界、阶段、真元、修为。
- `personality`：野心、谨慎、忠诚、贪欲、好奇。
- `schedule`：默认日程，不是强制剧本。
- `goals`：当前目标与候选目标。
- `memory`：事实索引和带时间/情绪的事件记忆。
- `inventory`：资源和蛊虫组件。
- `body`：生命、伤口和部位耐久；冲突系统只能通过伤害事件修改它。
- `abilities`：蛊术与技能能力槽，供行动系统消耗和验证。

NPC 行为运行时位于 `src/npc-ai.js`。它只依赖组件查询、地点图、时钟、随机源和 GoalHandler 回调：先由恐惧、饥饿、野心等需求覆盖默认日程，再沿地点图移动，最后执行目标并记录遭遇记忆。具体的 `secureResources`、`prepareAlliance` 等目标仍由内容规则注册，因此同一 AI 层可以服务青茅山 NPC、北原部族或未来其他内容包。

`factions` 和 `relationships` 独立保存，不能通过截断日志重建。这样玩家帮助方正、威胁漠北、向家族报告遗藏等动作，才会成为后续世界的事实，而不是一行已经消失的文字。

地点不是静态背景。`zones` 保存资源、天气、危险度、活动度、访问量和人口规模；人口表按地点类型生成环境居民，让竹林、河滩、商队营地和山寨在没有剧情事件时也能自行运转。资源采集、NPC目标和跨日恢复共同改变区域状态。

## 时间与 NPC

每个合法行动推进小时。时间推进触发：

1. 玩家需求、真元和修为恢复/消耗。
2. NPC 根据日程移动。
3. NPC 根据饥饿、恐惧、野心和世界压力选择当前目标。
4. 同场遭遇写入 NPC 记忆。
5. 跨日后结算需求、势力紧张度、导演压力和记忆衰减。

日程是“默认行为”，记忆和关系可以覆盖它；这使 NPC 不是静态对话点。导航系统在地点图上计算路径，每个行动周期只前进一个区域，因此跨地点目标不会瞬移，也不会因为不是直接邻居而失效。

NPC 目标还必须产出世界侧结果：采集会改变资源与势力影响，追查遗藏会增加共享压力，交易会改变商路活动，竞争会提高家族紧张度。日志只是这些事件的投影，不能代替状态本身。

## 事件和 AI 导演

事件分为两类：

- `action`：玩家提出的明确动作，由规则验证并结算。
- `director_event`：导演观察世界条件后生成的局势节点，例如竹林酒香、学堂竞争、商队消息。
- `combat`：实体间的连续冲突；攻击写入身体部位、伤口、死亡和对方记忆。

规则事件会写入带持久 `sequence` 的 `events.pending` 领域事件流，例如 `world.travel`、`npc.goal_action`、`social.interaction` 和 `combat.damage`。队列只保留最近窗口，但序列号不会回绕；外部导演、调试器或未来的回放系统可以消费这些事件，不需要解析 UI 日志。

运行时还提供事件监听器注册表。事件发出后，监听器可以为区域活动、危险度或统计账本添加派生后果；例如移动事件由区域访问监听器结算，演武和传承事件由各自的区域压力监听器结算。监听器不替代持久事件队列，而是把 Qud 式事件边界变成可组合的规则扩展点。

导演不能直接写玩家数值。它只能从世界状态中提出有条件的事件选择；`resolve_event` 仍经过同一个状态结算入口。当前导演已经覆盖遗藏线索、学堂竞争、商队进入、贾富拍卖会、三寨议事、狼潮逼近、三族大比武和铁家调查；后两者还演示了 NPC 的延迟生成。这些事件由时间、地点、势力紧张度、资源压力共同触发，而不是按章节顺序强制播放。将来接入语言模型时，模型只能生成候选意图/文案，不能绕过 `dispatch`。

## 小说迁移策略

第一阶段只迁移原文中有明确依据的青茅山开局：

- 方源重生与开窍大典前夜；
- 方正的孪生兄弟关系；
- 古月学堂、家老、竞争者和家族培养；
- 竹林、酒香、月光蛊、酒虫和花酒遗藏线索。
- 商队提前进入青茅山、贾富的市场博弈、三寨联盟和狼潮前的资源危机。
- 第二卷首批区域链：白骨山旅途、商家城演武场、三叉山三王传承、天梯山狐仙福地传闻。

后续卷章不会被硬编码成主线树，而是拆成地点、人物、势力、资源、事件条件和历史事实。每次新增内容都必须能回答“它改变了哪些状态、哪些系统会观察到它、哪些 NPC 会记住它”。
