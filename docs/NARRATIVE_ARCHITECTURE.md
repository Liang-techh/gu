# 叙事与视觉架构 0.3

## 目标

游戏不是把小说做成“下一页”阅读器，而是让世界状态决定哪些剧情出现。视觉层可以越来越丰富，但不能直接修改存档中的修为、元石、关系或剧情标记。

## 四层职责

### 1. 表现层

`visual-ui.js` 与 `visual-v3.css` 负责场景、人物剪影、剧情对话框、战斗舞台、地图视觉标记和剧情图。它只读取自动存档快照和现有 DOM；需要真正行动时，仍然点击 / 调用原有交互按钮，让 `engine.dispatch` 结算。

### 2. 叙事组织层

`narrative.js` 提供：

- 地点的视觉主题和场景短句
- 人物视觉标识
- NPC 话题列表与安全条件
- 剧情节点所属分组

`content.js` 仍然保存真正的事件、选择、条件和效果。这样场景换图、改 UI、加配音时不需要碰规则数据。

### 3. 世界规则层

`engine.js` 是唯一权威规则入口：

- 时间推进
- 真元 / 元石 / 修行
- 人物关系和记忆
- 借债 / 市场 / 商队
- 战斗
- 条件检查
- 延迟事件队列

表现层禁止直接改这些值。

### 4. 存档层

原 0.2 schema 与键名不变。0.3 没有新增必须持久化的规则字段，因此旧存档不需要迁移。

## 因果图生成

因果图不维护第二份剧情树。它直接遍历 `D.events`：

1. 每个事件成为一个节点。
2. `choice.effects.schedule` 中的目标成为有向边。
3. `state.seen` 标记已发生节点。
4. `state.pending` 标记当前节点。
5. `state.queue` 标记等待中的后果。

因此新增一个带 `schedule` 的事件后，图会自动显示其后续关系。

## NPC 话题的下一步

0.3 先把“一个交谈按钮”变成条件化话题菜单，但最终应继续升级为数据驱动的对话节点，例如：

```js
{
  id: 'ask_exam',
  person: 'fangzheng',
  requires: [['npcs.fangzheng.trust','>=',20]],
  text: '……',
  effects: {
    relation: { fangzheng: { trust: 2 } },
    schedule: [['exam_followup', 24]]
  }
}
```

这类节点应该由引擎统一校验和结算，而不是把效果写在 DOM 事件中。

## 美术替换原则

当前场景和人物使用本地 CSS 构图，是为了先完成系统接口。未来正式美术应只替换：

- location → background
- person → portrait / expression
- gu → card art
- event → optional CG

禁止让图片文件承载游戏状态。存档只保存语义 ID，不保存图片路径或临时 DOM 状态。
